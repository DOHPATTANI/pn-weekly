# UI Release Gate — เกณฑ์บังคับก่อนเผยแพร่

เจ้าของเกณฑ์นี้คือเอกสารฉบับนี้ AGENTS.md และ workflow อ้างอิงแทนการทำสำเนา ใช้กับทุกงานที่เปลี่ยน UI รวมถึง shared CSS และ DOM mounting

## 1. ก่อนแก้ไข

- ระบุหน้าที่ได้รับผลโดยตรงและหน้าที่ใช้ shared component/CSS เดียวกัน
- อ่าน DESIGN.md, UX-CONTRACT.md และตรวจ DOM/CSS owners จริงก่อนเสนอ layout
- เทียบหน้าปัจจุบันกับแบบที่ผู้ใช้อนุมัติ ระบุจุดต่างใน acceptance matrix ห้ามใช้ความจำหรือ build ผ่านเป็นหลักฐานว่าหน้าตาตรงแบบ
- ออกแบบลำดับเดียวกัน: ชื่อหน้า → ขอบเขตข้อมูล → ค้นหา/ตัวกรอง/คำสั่ง → สรุป → ตาราง โดยยุบขั้นที่รวมกันได้ ไม่มีแถบแยกเพียงเพื่อวางปุ่มเดียวโดยไม่มีเหตุผลด้านงาน

## 2. ข้อผิดพลาดที่ห้ามผ่าน release

| ประเด็น | เกณฑ์รับงาน | หลักฐานที่ต้องมี |
|---|---|---|
| ตัวกรองซ้ำ | กลุ่มงบ/ปีส่วนกลางมีอย่างละหนึ่งชุด ID ไม่ซ้ำ หน้าที่ต้องมี scope ต่างกันต้องระบุชื่อและเหตุผลชัด เช่น ประวัติทุกปี | DOM assertion และสลับขอบเขตจริง |
| กรอบว่าง/พื้นที่เกินจำเป็น | ไม่มี border/padding/min-height ของ container ที่สูญเสีย controls หลังย้าย DOM ไม่มีกรอบเปล่าหรือแถวว่างระหว่าง controls กับข้อมูลโดยไม่มีหน้าที่ | ภาพหลัง render และหลังสลับหน้า |
| คำสั่งกระจัดกระจาย | ปุ่มหลักหนึ่งตำแหน่งที่ชัดเจนชิดขวาของกลุ่มคำสั่ง ปุ่มรองรวมเมนู ไม่มี CTA ซ้ำจากการ clone หรือตกค้าง | ภาพและ click/keyboard checks |
| แถบตาราง | ค้นหาซ้าย ตัวกรองติดกัน เครื่องมือเลือกหลายรายการ/จำนวนแถวชิดขวา อยู่ในกรอบเดียว ไม่มีกรอบซ้อนเพื่อห่อแถบเดียว | ภาพและตรวจ DOM |
| การ์ดสรุป | ความสูง/spacing เป็นระบบ จำนวนคอลัมน์ตั้งใจตาม viewport ไม่เกิดการ์ดเดี่ยวตกแถวบน desktop เพราะใช้จำนวนคอลัมน์ผิด | screenshot desktop/tablet/mobile |
| ป้าย/สี | ป้ายอยู่ติดช่อง สีสถานะตรงกติกาผู้ใช้และมีข้อความกำกับ ไม่ใช้สีตกแต่งที่ขัดความหมาย | ตรวจค่าจริงทุกสถานะที่เปลี่ยน |
| ตาราง/Responsive | ทั้งหน้าไม่ล้นแนวนอน ตารางเลื่อนใน container ของตัวเอง mobile cards ใช้ label/value; Dashboard/รายงานคงข้อยกเว้นเดิม | DOM dimensions และ browser test |
| โหมด/เมนู | ทดสอบ Sidebar ขยายและย่อ เมนูเปิด/ปิด ฟิลเตอร์ยุบ/ขยาย ไม่บังหรือดัน controls ผิดตำแหน่ง | ภาพและ interaction checks |
| เอกสารราชการ | UI CSS ไม่รั่วเข้า preview/PDF/ภาพ/Excel ของรายงานที่อยู่นอกขอบเขต | targeted export regression |

ข้อผิดพลาดในตารางเป็น release blocker สำหรับหน้าที่ได้รับผล ห้ามลดเกณฑ์ ปิด test หรือเปลี่ยน baseline เพื่อทำให้ความผิดพลาดผ่าน

## 3. Browser evidence ก่อน push ที่นำไป deploy

1. รัน source generation, focused tests และเปิดเว็บจากโค้ด revision เดียวกัน
2. ตรวจทุกหน้าที่ได้รับผลที่ desktop 1440 หรือ 1500px, tablet 768px และ mobile 375px รวม breakpoint 640px หากเปลี่ยนตาราง เกณฑ์ viewport ของโครงการที่กว้างกว่านี้ยังคงใช้
3. ถ้าแก้ shared shell/toolbar/tokens ต้องตรวจทุกหน้าหลัก ไม่สุ่มเพียงหน้าเดียว ตรวจ Sidebar ทั้งสองโหมดอย่างน้อย desktop
4. เก็บภาพหลังฟอนต์/ข้อมูล/DOM mounting เสร็จและปิด toast ที่บังหน้า ตรวจซ้ำหลังสลับหน้า เปลี่ยน scope และเปิดเมนูที่เกี่ยวข้อง
5. ตรวจภาพด้วยสายตาจริง เทียบลำดับข้อมูล ความหนาแน่น alignment spacing และ hierarchy กับแบบที่อนุมัติ พร้อมบันทึก Pass/Fail/Not run และไฟล์ภาพใน work/ ใช้ข้อมูลทดสอบที่แยกจาก production หรือปกปิดข้อมูลอ่อนไหวในหลักฐาน
6. เมื่อมี baseline ที่อนุมัติ ให้รัน screenshot comparison ด้วย หากยังไม่มี ห้ามสร้าง baseline จาก implementation แล้วอ้างว่าตรงต้นแบบ การตรวจ screenshot ด้วยสายตาต้องระบุให้ชัดว่าไม่ใช่ pixel comparison
7. ถ้า browser ใช้ไม่ได้ให้ใช้ fallback ตาม AGENTS.md แต่สถานะ visual ยังเป็น Not run และห้ามประกาศว่า visual ผ่านหรือพร้อมด้านหน้าตา

## 4. การตัดสินผลและเผยแพร่

- Unit tests, build, HTTP 200 และไม่มี console error ยืนยันคนละเรื่องกับคุณภาพหน้าตา ไม่ทดแทน visual review
- บันทึก acceptance matrix ของ scope จริงให้ครบทุกข้อก่อนอ้างงานทั้งหมดเสร็จ รายการ Pending/Not run ต้องไม่ถูกเขียนเป็น Pass
- ตรวจ reviewer ด้วยบทบาทเดียวได้ ไม่บังคับเพิ่ม agent หรือขอผู้ใช้ยืนยันซ้ำ แต่ต้องตรวจผลหลังแก้จริงและห้าม auto-pass จาก runner
- หลัง deploy ตรวจ revision ของ live assets, boot/navigation, controls ไม่ซ้ำ และหน้าที่แก้ทั้ง desktop/mobile แบบ read-only ห้ามแก้ข้อมูลจริงเพื่อ smoke test
- ถ้าพบ regression ให้แก้และผ่าน gates ที่ได้รับผลอีกครั้ง ห้ามส่งมอบเป็นพร้อมใช้งานทั้งที่รู้ว่าหน้าตายังผิดเกณฑ์
- งาน UI ต้องมีหลักฐานก่อน/หลังและผลตรวจที่เชื่อมกับ revision เสมอ ความเห็นผู้ใช้ที่ชี้ regression ต้องถูกเพิ่มเป็น acceptance criterion เพื่อป้องกันเกิดซ้ำ
